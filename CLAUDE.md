# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Falken's Lab's marketplace (`falkenslab`) of extensions. Each extension folder is both a Claude Code plugin, unchanged, and an extension for agents built on [agent-kit](https://github.com/falkenslab/agent-kit). Besides JSON manifests, Markdown skills and commands, SVG assets, a static catalog page and `scripts/check-tools.mjs`, it holds the `weather` example server (inside its extension) and, in `mcps/`, the servers that exist for these extensions (`anki`, `asker`, `calendar`, `documents`, `h5p`), each published to npm on its own; servers with users of their own (moodle-mcp, docker-mcp, teuton-mcp) keep their own repositories.

## Commands

Node 22, no dependencies, no `npm install` at the root.

- `npx -y @falkenslab/agent-kit-catalog@0.7.0` rewrites `catalog.json` from the manifests. Run it after any change to `.claude-plugin/marketplace.json` or an extension's `plugin.json`, and commit the result. The generator lives in agent-kit (the `agent-kit-catalog` package), with the catalog's format; bump its pinned version here and in both workflows together.
- `npx -y @falkenslab/agent-kit-catalog@0.7.0 --check` fails if `catalog.json` is stale (CI runs it in both workflows).
- The links point to `--repo owner/name`, else `GITHUB_REPOSITORY`, else the `origin` remote, else the `repository` shared by every `plugin.json`; the branch is `--branch`, else always `main` (never the checked-out one, so the output is the same on every branch).
- `node scripts/check-tools.mjs [extension…]` starts each local MCP server at its pinned version (only `tools/list`: no Moodle or Docker needed) and fails if a capability, a label, `readOnlyTools`, `confirmTools`, `serverConfirmTools`, a skill or a command names a tool its server doesn't have in that role, if `readOnlyTools` leaves out a tool the server marks read-only, if a tool has no label (in an extension that labels its tools), or if a README quotes another version of a pinned server or its "What's inside" table (`## 🧰`) leaves out or invents a skill, a command or a subagent. CI runs it; run it after bumping a server.
- `claude plugin validate --strict .` validates the marketplace; `claude plugin validate --strict extensions/moodle-teacher` validates one extension. Strict means warnings fail. `userConfig` with `options` needs Claude Code 2.1.271 or later.
- `extensions/weather/` builds its own MCP server: `npm install` and `npm run build` in `extensions/weather/` write its `dist/server.mjs`, which is committed (agent-kit installs files and never runs `npm install`); its `node_modules/` stays out. Rebuild it after any change to `weather/src/`.
- `mcps/<name>/` is a server published to npm as `@falkenslab/<name>-mcp` (only its `dist/server.mjs` goes in the package): `npm install`, `npm run build` and `npm test` there. `h5p` and `asker` are TypeScript, with `typecheck`, `lint` and `check` too; `asker` runs Asker (Ruby and the asker-tool gem): its tests use a fake one, and the real one too when it's installed, which CI does (`ASKER_MCP_REAL_TESTS=required`), and `scripts/capture-fixtures.mjs` refreshes what the fake answers. A server not yet on npm has its build also copy `dist/server.mjs` into `extensions/<name>/dist/`, committed, which the extension runs until its `.mcp.json` moves to `npx -y @falkenslab/<name>-mcp@<version>` (then that copy goes). CI builds and tests each one and fails if the committed copy is stale. A version goes up together in `package.json` and the server's `VERSION` constant (and, while bundled, the extension's `plugin.json`); `npm publish` (the owner's) builds and tests first, and only then does the extension pin it. Those on npm run with `npx` from their extensions. Code that only builds or tests a server lives there, never in the extension, since agent-kit installs an extension's whole folder.
- To try an extension in an agent: `my-agent extension add ./extensions/moodle-teacher --link`.
- To preview the site, serve the repository root over HTTP and open `site/index.html` or `site/catalog.html` (they fetch `catalog.json` or `../catalog.json`).

## How the pieces fit

- **`.claude-plugin/marketplace.json`** lists every extension with `source`, `version`, `category` and `tags`. The `version` must equal the one in the extension's `plugin.json`; the catalog generator fails otherwise. Only local `./folder` sources are supported by the catalog.
- **An extension** (a folder under `extensions/`, e.g. `extensions/moodle-teacher/`) has `.claude-plugin/plugin.json`, `.mcp.json`, `skills/<name>/SKILL.md`, `assets/` and a `README.md`. A flow the person starts ("this week", "what to grade") is a skill, not a command: Codex loads skills but not commands, and Claude Code offers a plugin's skills as `/plugin:skill` too; only weather keeps a command (`/today`), which agent-kit's tutorial teaches. A skill whose frontmatter has a `label` (`es=… | en=…`), with `icon`, `group` (`day`, `create`, `plan`, `memory` or `classroom`) and `needs-classroom`, is also a button on miyagi's pages (moodle-teacher's `week`, `to-grade`, `course-check` and `class-progress`, asker's `asker-questions`); Claude Code and Codex ignore those keys, and padawan doesn't read them yet. An extension can also bring subagents (`agents/<name>.md`: asker, moodle-teacher, docker-lab), for work that reads a lot and returns a short report; a subagent without `tools` inherits the session's, write tools included, in Claude Code and agent-kit alike (their MCP tool names differ, so don't list them), so its instructions say it only reads; in agent-kit it gets no `Bash`. And hooks (`hooks/hooks.json`: asker, docker-lab, canva): only Claude Code runs a plugin's hooks (agent-kit doesn't, and Codex 0.163 lists `plugin_hooks` as removed), so a hook only repeats what a skill already says, adds context (`additionalContext`, also in `PreToolUse`) rather than asking or denying, and its script uses nothing but Node.
- **`.mcp.json`** runs the MCP server: the two moodle extensions' from npm at the same exact pinned version (`npx -y @falkenslab/moodle-mcp@0.11.1`; bump both together), each with its role fixed (`MOODLE_MCP_ROLE`: `teacher` or `student`), and maps `userConfig` values into env vars with `${user_config.<key>}`. Bumping the server version is an edit here, and so is their `readOnlyTools`: once a manifest lists it, the kit stops reading the servers' `readOnlyHint`, so it's every tool the new version marks read-only for the role (from its `tools/list`) plus `login`, `logout`, `show_browser` and `use_site`, which change no course. Their `serverConfirmTools` is redone with it too. weather's runs its bundled `dist/server.mjs` with `node ${CLAUDE_PLUGIN_ROOT}/dist/server.mjs`. canva's is Canva's own remote server (`"type": "http"`, `https://mcp.canva.com/mcp`), signed in with OAuth from the chat, so it has no `Authorization` header (one turns the CLI's OAuth off) and lists its read-only tools in `readOnlyTools`.
- **`plugin.json` `userConfig`** is the settings asked at install time. Its keys must match the `${user_config.*}` references in `.mcp.json`.
- **`plugin.json` `metadata["agent-kit"]`** is read only by agent-kit: `description` with the extension's description in Spanish (`{ "es": "…" }`; English stays `plugin.json`'s own `description`, which Claude Code and Codex read), `catalog.logo` (square) and `catalog.banner` (wide) as paths inside the extension folder, `provides`/`requires`, `capabilities`, `requirements`, `readOnlyTools` (what only reads: plan and guided mode let it through; else the servers' `readOnlyHint`), `confirmTools` (what always asks in guided mode and is never offered "always", for what can't be undone or others see; else the servers' `destructiveHint`, which moodle-mcp and docker-mcp set), `serverConfirmTools` (what its server confirms itself through elicitation, so guided mode doesn't ask too: one question, the server's; moodle-mcp's always-confirmed tools, from its `src/tools/confirm.ts`, not those it confirms only in some calls), a `help` line, and `labels` giving each MCP tool a progress label and singular/plural phrase in `en` and `es`. A new tool in the MCP server should get a `labels` entry in both languages. `agent-kit-catalog` rejects any other field there.
- **Capabilities** (skills + tools = capabilities): each extension declares what it lets the agent do as `capabilities`, `{ id, skills, tools, texts }`, with `texts.en` and `texts.es` (`label`, `description`) written for the person. Ids are kebab-case and neutral (`lms-grading`, not `moodle-grading`), so miyagi's and padawan's skills `requires` them whatever extension provides them; where a capability means something different per role, the ids differ (`lms-forums` for running forums, `lms-forum-participation` for taking part). Every skill a capability names must exist, and every tool must exist in its server and role. `provides` keeps the extension's names and its umbrella (`lms-teacher`, `lms-student`).
- **Requirements**: an extension whose server uses a program the person installs apart (Docker, ffmpeg) declares it in `requirements`, `{ name, program, version?, install, for? }`, with an install command per system and the capabilities that need it; its server also offers a read-only `check_requirements`. Extensions that need nothing declare nothing.
- **Topics** shown in the catalog are the union, lowercased, of `plugin.json` `keywords` plus the marketplace entry's `tags`, `keywords` and `category`. An audience is a topic too (`miyagi`): agent-kit agents offer their users only extensions matching their `catalogTopics`.
- **`catalog.json`** is generated, never edited by hand. Image paths become `raw.githubusercontent.com/.../main/...` URLs, so assets must exist and be committed on `main`.
- **`site/`** is the public site, reading `catalog.json`: `index.html` (the home page: the hero and the marketplace's install commands per client) and `catalog.html` (search, topic chips, `?topic=` filter, and each extension's card with how to install, configure and use it per client, and its technical sheet: servers, skills, commands, subagents and tools by capability, from `catalog.json`), sharing `site.css` and `site.js`; light, dark and system themes. `index.html?topic=…` redirects to the catalog, for links made before it had its own page. The `pages` workflow publishes `site/` and `catalog.json` to GitHub Pages on every push to `main`.

## Conventions

- `.gitattributes` forces LF everywhere because agent-kit verifies extension files by hash; don't introduce CRLF.
- Skills (and weather's command) are written to the agent, in English, telling it how to use the MCP tools well (name the actual tool names, say what needs the person's approval, and whether a command only reads).
- An extension brings what an agent doesn't have: a platform (Moodle, Classroom), an external service (katalog, Canva), a file format (documents, H5P, Anki, ICS) or a tool (Docker labs, video). Never a country's or a region's education law, curriculum or school calendar, nor one extension per stage (primary, secondary, VET, university): the teacher brings the norms that apply to them as their own sources, and interpreting them is the agent's craft (#3). The craft of teaching or studying is never an extension: planning, assessing, reviewing or learning a language belong to miyagi or padawan, whose skills use extensions through their capabilities.
- An extension knows its platform, not the domain around it: the `moodle-teacher` and `moodle-student` skills say how things are done in Moodle (settings, tools, what Moodle imposes), never how to teach or to study. That practice lives in the agent that installs the extension (miyagi for teachers, padawan for students). Every tool a skill names must exist in the pinned server version and in its role (moodle-mcp's tools reference marks each tool's roles); where none covers a task, say so and fall back to the person or to the `browser_*` tools with their yes.
- **Codex** installs these extensions from `.claude-plugin/marketplace.json` too (checked with Codex 0.146), loading their skills and MCP servers, but it has no `userConfig`, no commands and no `metadata["agent-kit"]`, and it doesn't expand `${CLAUDE_PLUGIN_ROOT}` in `.mcp.json`. So, for an extension to work there: run its server with `npx -y <package>@<version>` (not from its folder), have the server treat a setting left as a literal `${user_config.*}` as not set and ask for it in the chat, and keep every flow in skills, not only in commands. Codex keeps one MCP server per name across plugins: `moodle-teacher` and `moodle-student` both name theirs `moodle`, so their READMEs say to enable only one there.
- When adding an extension, also add its row to the extensions table in the root `README.md`.
- Writing an extension is documented upstream: [Writing an installable extension](https://falkenslab.github.io/agent-kit/docs/extensions/writing), whose tutorial builds `extensions/weather/`.
